## 1. この長期開発のねらい

ai01〜ai06で、子どもたちは次のことを身につけてきました。AIを知る、問いを立てる、言葉でアプリを作る、設計書と完成の基準を書く、エージェントに任せて検証する、エディタの中のAIと開発する。

長期開発では、これらを1つの作品に注ぎこみます。新しく足すことは1つだけです。

**子どもは「プログラマー」ではなく、「AIの監督（プロデューサー）」になる。**

コードを書く力は求めません。求めるのは次の4つです。

- 何を作りたいかという**意志**
- それを相手に伝わるように**言葉にする力**
- 出てきたものを見て「これだ」「違う」と分かる**判断**
- 本当にできているかを**確かめる力**

研究でも、AIを使いこなす中心の力は技術ではなくマネジメントの力（任せる・伝える・確かめる・決める）だ、という見方が主流になっています（19章）。

冒頭でこう言い切ってください。**「君はプログラマーじゃない。監督だ。作るのはAI、決めるのは君」**

## 5. AI駆動開発の本質（先生の考え方の軸）

### 5-1. 方法ではなく理想を渡し、判断は人間が持つ

**指示は、そのまま作品の天井になります。** 「Canvasで、敵が左から右に動いて、スペースキーで弾を撃つゲーム」と頼めば、AIはその通りに作ります。上限は子どもが知っている方法の範囲になり、AIの知識はほとんど使われません。

最新のモデルは指示に忠実になった分、**狭い指示には狭く正確に応えます。** 野心的なものがほしいなら、そう伝える必要があります。

| 方法を指示する | 理想を渡す |
|---|---|
| 「Canvasで、敵が左から右に動くシューティング。弾はスペースキー」 | 「友達が『あと1回だけ』をやめられなくなる、手に汗をにぎるゲームにしたい。スマホでも遊べて、費用はかからないこと。どんな形がありえるか、まったく違う方向で5つ提案して。それぞれ、なぜ『あと1回』になるのかも」 |
| 「掲示板を作って。名前と本文を入力できるようにして」 | 「クラスの中で、普段話さない人どうしが自然に話すきっかけになる場所を作りたい。どんな仕組みならそうなる？」 |

### 5-2. 理想はぼんやりではなく、体験として鮮明に

- 「かっこいいゲーム」→ ぼんやりしているので、AIは平均的なものを返す
- 「負けた瞬間に悔しくて、指が勝手にリトライを押す」→ 方法は何も決めていないのに、体験は鮮明

**方法は自由に、体験は鮮明に。** 細かすぎる手順と、ぼんやりした抽象論の間にある「ちょうどいい高さ」で書きます。

### 5-3. 広げてから絞る

絞ることは悪くありません。悪いのは**早すぎる絞り込み**です。

- **広げる時期**（企画、新しい機能の最初）：問いで渡す。「どうすれば〜になる？」「誰もやっていない方向は？」
- **絞る時期**（形が見えたあと）：子どもの具体的な判断で絞る。「この揺れは強すぎる」「こっちの色」

### 5-4. 柵は外側だけ：地面は固めて、空は開ける

| | 固める（地面） | 開ける（空） |
|---|---|---|
| 中身 | 安全、費用ゼロ、公開の仕組み、鍵の扱い | 何を作るか、どう実現するか、どんな体験にするか |
| 目的 | 安心して大胆になれるようにする | 可能性を最大にする |

テンプレートやAGENTS.mdのルールは「やり方を縛るため」ではなく「守るため」だけに置きます。

### 5-5. 人間の仕事は「意志」と「判断」

AIは、ほぼ何でも作れます。でも、**何を作りたいかは持っていません。** 子どもの「これが好き」「こういうのが悔しい」は、AI時代の一番の資源です。

### 5-6. 理想は、AIとの往復で育てる

**理想を渡す → AIが提案する → 作って触る → 判断する → 理想が育つ → また渡す**

「これを見て、本当にやりたいのは対戦じゃなくて協力だと気づいた」は失敗ではありません。作品が子どもの想像を超えた瞬間です。

### 5-7. モデルが賢くなるほど得をする作り方

方法を細かく指示した作品は、モデルが賢くなっても良くなりません。理想を渡す作り方なら、同じ理想から出てくるものが自然と良くなります。

### よくある誤解

| 誤解 | 本当は |
|---|---|
| 理想を渡す＝丸投げ | 判断は手放さない。選ぶ・断る・方向を示すのは人間 |
| 理想＝ぼんやりでいい | 方法は自由に、体験は鮮明に |
| AIの提案は最高のもの | AIは無難な案に寄りやすい。「大胆な案を1つ」と振れ幅を求める |
| 大きな理想は時間内に終わらない | 理想は大きいまま、今回作る範囲だけ絞る |

## 6. AIは「天才の部下」だが、人間とは違う

AIを扱うのは、優秀な人材をマネジメントするのに近い仕事です。ただし、人間の天才と同じに扱うと失敗します。正確なたとえは次のとおりです。

**「毎朝記憶を失い、得意と苦手の差が極端で、相手に合わせて『できました』と言いがちな天才。何人でも雇えて、何度でもやり直させられる」**

| 人間の天才 | AI | だから、こうする |
|---|---|---|
| 記憶が続く | 会話が変わると記憶がない | ドキュメントで引き継ぐ（8章） |
| 得意・苦手がある程度読める | 得意と苦手の境界がギザギザで、もっともらしく失敗する | 必ず確かめる。基準で見る |
| 違うと思えば反論する | 相手に合わせがち（迎合） | 批判を求める。別の会話でレビューさせる |
| やり直させると士気が下がる | 何度やり直しても平気 | 3案作らせて2案捨ててよい |
| 意図を持ち、責任を負う | 意図も責任も持てない | 「十分か」「公開するか」を決めるのは人間 |

### 研究から分かっている注意点

- **「社員扱い」すると、確認が甘くなる。** 同じ下書きでも「AI社員が書いた」と表示するだけで、管理職のチェックが16%減ったという報告がある（セミナーの要旨段階）。
- **体感と実際はずれる。** 熟練の開発者がAIを使うと、実際は19%遅くなったのに、本人は20%速くなったと感じていた（METR、2025年）。
- **完全に任せきれる仕事は一部。** Anthropicのエンジニアでも、完全に任せられるのは仕事の0〜20%で、残りは確認と監督が必要。
- **監督のパラドックス。** 監督にはスキルが要るのに、任せすぎるとそのスキルが衰える。このコースでは**コードではなく、体験と基準で監督する**ことで、この問題に答える。

### 監督の6つの力

| 力 | 内容 | このコースでの形 |
|---|---|---|
| 1. 目的を伝える | 何のために、何を達成したいか | 企画書（理想の6要素） |
| 2. 任せる範囲を決める | 小さく任せて、信頼を広げる | 1回に1つ → 慣れたら大きく |
| 3. 確かめ方を先に決める | 何ができたら合格か | タスク.mdの確かめ方 |
| 4. フィードバックを返す | 何が良くて何が違うかを具体的に | バグの伝え方、「Aの動きとCの色」 |
| 5. 疑う | 「できました」をうのみにしない | 別の会話でのレビュー、壊し方を出させる |
| 6. 決めて、責任を持つ | 選ぶ・断る・十分かを決める | 公開の判断は本人と先生 |

### 7-1. スターターテンプレート

- 「画面 ＋ Worker ＋ D1 ＋ AI中継Workerへの接続」が、最初から動く状態にしておく。
- 子どもが中身を考えることだけに時間を使えるようにする。土台の構成をAIに選ばせると、毎回違う構成を作り、途中で書き直し始めるため。
- ai07の前に、全員分を先生がデプロイしておく。初回から自分のURLがある状態で始める。

### 7-2. AGENTS.md

実際に使うものは `ai07/files/AGENTS.md` と `ai07/files/docs/` の3つのファイル。技術と安全の決まりだけを書き、作品の中身や作り方の指示は入れない（冒頭の「最新の決定」）。

### 7-3. 部品レシピ集（recipes/）

DeepSeekは、Cloudflare特有の書き方について知識が古かったり、間違えたりします。お手本があると成功率が段違いに上がります。子どもは「recipes/ランキング を参考にして、私の作品にランキングを付けて」と頼むだけで済みます。

| レシピ | 中身 | 対応する天井 |
|---|---|---|
| ランキング | D1に保存、上位10件を表示 | 段階2 |
| みんなの投稿 | 投稿・一覧・AIの事前チェック | 段階2・4 |
| AIと会話 | AI中継Workerを呼ぶ、キャラの指示文 | 段階4 |
| AIが作るデータ | DeepSeekにJSONでステージやアイテムを作らせる | 段階4 |
| リアルタイム | Durable Objectsで、複数人が同じ部屋に入る | 段階5 |
| 毎日変わる | Cronで、毎朝データを更新 | 天井：毎日変わる世界 |
| 画像を置く | R2に保存して表示 | 段階2 |
| クラス通貨 | 先生の共通通貨Workerを呼ぶ | 天井：経済圏 |
| 手・顔の認識 | MediaPipe の最小例 | 段階3 |
| 声で操作・読み上げ | ブラウザの音声認識・音声合成 | 段階3 |

### 7-4. AI中継Worker

- DeepSeekの鍵は、先生専用の中継Workerにだけ置く。生徒の作品は中継Workerを呼ぶだけにする。
- 中継Workerで、生徒ごとの1日の回数上限と、不適切な出力のフィルタをかける。
- DeepSeekは前払いの残高制なので、残高がなくなれば止まるだけで、請求が膨らむことはない。
- 生徒の作品と中継Workerは、同じアカウント内のWorkerどうしをつなぐ仕組み（Service Binding）で接続する。生徒の手元での動作確認のときにどうつなぐかは、テンプレートを作るときに検証して決める。
- Zedで開発に使うキー（ai06の授業用キー）とは別物。Zed用のキーは今までどおり、授業後に削除する。

## 8. 作品フォルダとドキュメント

### 8-1. フォルダの形

```
（作品フォルダ）
├─ AGENTS.md            … AIの約束（先生が用意）
├─ docs/
│  ├─ 企画書.md          … 理想（本人が考え、AIが整える）
│  ├─ 仕様書.md          … 何を作るか（AIが書き、本人が直す）
│  ├─ タスク.md          … 機能の一覧・確かめ方・済みの印
│  ├─ 決めたこと.md      … 決定・理由・採用しなかった案
│  ├─ 開発日誌.md        … 毎回の引き継ぎ
│  └─ ライブラリ.md      … 使ってよいライブラリ（先生が用意）
├─ recipes/             … 部品レシピ（先生が用意）
├─ public/              … 画面
├─ src/                 … サーバー（Worker）
└─ wrangler.jsonc       … Cloudflareの設定（触らない）
```

ai06の docs/企画書.md・仕様書.md・タスク.md をそのまま引き継ぎ、3つのファイルを足しています。

### 8-2. なぜドキュメントが要るのか

- **AIには会話をまたいだ記憶がない。** Anthropicはこれを「交代制の現場で、新しく来るエンジニアが前のシフトの記憶を一切持っていない状態」とたとえている。解決策も人間と同じで、引き継ぎメモ・履歴・完成と言う前のテスト。
- **子どもも忘れる。** 月1回だと、前回何を決めたかを本人も覚えていない。
- **AIが方針をひっくり返すのを防ぐ。** 理由が書いていないと、AIは新しい会話のたびに別の方向へ作り変えようとする。
- **長い会話は質が落ちる。** 機能ごとに新しい会話に切り替えても、状態はドキュメントが運ぶ。
- **それ自体がマネジメントの練習になる。** AIのまとめを読んで「ここは違う」と直すことが、目的を伝える・確かめる練習になる。

**1回の授業が1シフト、ドキュメントが引き継ぎ。**

### 8-3. 各ドキュメントのルール

| ファイル | 中身 | 誰が書く・変えるか |
|---|---|---|
| 企画書.md | 理想の6要素、伝説版と今回の範囲 | 本人が考え、AIが整える。変更は本人の許可が必要 |
| 仕様書.md | 画面、データ、機能の一覧（MVP・次・いつか） | AIが書き、本人が読んで直す |
| タスク.md | 1回30分で終わる大きさのタスク、確かめ方、済みの印 | AIは済みの印を付けるだけ。削除・書き換えは禁止 |
| 決めたこと.md | 決めたこと、理由、採用しなかった案 | 大きな決定のたびにAIが追記し、本人が確認 |
| 開発日誌.md | 毎回やったこと、次にやること、困っていること | 毎回の終わりにAIが書き、本人が確認 |

タスク.mdのルールは、AIがこっそり項目を消して「全部終わりました」と言う事故を防ぐためのものです（Anthropicの実践から）。AIがよく表を崩すようなら、JSON形式に切り替えます。

### 8-4. 企画書.md の型（理想の6要素）

```markdown
# 企画書

## 1. 誰のために
（具体的な1人。「みんな」は不可）

## 2. どんな瞬間を生みたいか
（その人に何を感じてほしいか。方法ではなく体験で書く）

## 3. なぜ作りたいか
（自分の想い）

## 4. 守る条件
- 費用はかからない（Cloudflare Workers と AI中継Worker だけ）
- スマホでもPCでも遊べる
- 個人情報・人の作品を使わない

## 5. 成功したと分かるサイン
（何が起きたら成功か。例：初めての人が説明なしで30秒以内に遊び始める）

## 6. 任せる宣言
作り方は任せる。もっと良い理想があれば、理想そのものにも提案して。

## 伝説版と今回の範囲
- 普通版：
- すごい版：
- 伝説版：
- 今回の10時間で作る範囲：
- 一番の面白さ（ここだけは磨き切る）：
- 驚きの1つ：
```

### 8-5. タスク.md の型

```markdown
# タスク

- [ ] 敵に当たると、0.1秒止まって弾け飛ぶ
  - 確かめ方：10回当てて、毎回止まって弾ける
  - 優先：MVP
- [ ] ランキングを保存する
  - 確かめ方：2台のPCで遊んで、両方に同じ順位が出る
  - 優先：次
```

### 8-6. 使うタイミング

| タイミング | AIへの一言 |
|---|---|
| 授業の最初 | 「開発日誌・タスク・決めたことを読んで、今の状況と今日の候補を3つ報告して」 |
| 大きな決定のとき | 「今決めたことを、理由と採用しなかった案もつけて、決めたこと.mdに追記して」 |
| 授業の最後 | 「次の自分とAIへの引き継ぎを、開発日誌.mdに書いて」 |

**注意**：AIのまとめはうのみにしない（都合よく要約する、話を盛る）。短く保つ。古いドキュメントは、ないより悪い（AIは書いてあることに従ってしまう）。

## 10. 毎回の授業の型

### 120分の型

| 時間 | 内容 | AIへの一言 |
|---|---|---|
| 10分 | 思い出す | 「開発日誌・タスク・決めたことを読んで、前回どこまでやったか、今日の候補を3つ教えて」 |
| 80分 | 開発ループを何周も回す | 下の1サイクル |
| 15分 | セーブと記録 | 「ここまでをセーブして」「今日の引き継ぎを開発日誌に書いて」 |
| 15分 | 見せ合い | 隣の人に触ってもらう |

### 開発ループの1サイクル

1. **選ぶ**：タスク.mdからタスクを1つ選ぶ
2. **相談する**：Askモードで、どう作るかの計画を出させる。読んで納得してから進む
3. **作らせる**：Writeモードで作らせる。どのファイルが変わったかを見る。頼んでいないファイルが変わっていたら止める
4. **確かめる**：手元のブラウザで動かし、タスクの確かめ方と比べる
5. **セーブする**：動いたらセーブし、済みの印を付けさせる
6. **提案させる**：「私が思いつかないような改善を3つ。1つは大胆なもの」。採用するものをタスクに足す

動かなければ「困ったとき」へ：

1. バグの伝え方の型で伝える（11章）
2. 原因の仮説を3つ出させる
3. **3回直らなければ、最後のセーブに戻して、頼み方を変える**

### ループの考え方（先生向け）

この1サイクルは「人間が中に入ったループ」です。最近はAIが自分で回し続けるループを設計する考え方（ループエンジニアリング）も広まっていますが、このコースでは言葉や技術としては教えません。考え方だけ、すでに型の中に入っています。

| ループの要素 | このコースでの形 |
|---|---|
| ゴールと終わりの条件 | タスクの確かめ方 |
| 1周に1つ | 1回に1つ |
| 中での確認 | 動かして、基準と比べる |
| 回数の上限 | 3回直らなければ戻す |
| 記憶 | ドキュメントとセーブ（git） |

上位の子には、1回の依頼の中の小さなループまでは使わせてかまいません。

> 「作ったら自分でテストを実行して確かめて。失敗したら直す。これを最大3回まで繰り返してから、結果を報告して」

一晩中走らせる自律ループや、複数のエージェントを指揮する仕組みは使いません。残高を消費し、監督なしで作品を書き換えるためです。

## 11. AIへの頼み方集

### 発想：画期的にする

| 使い方 | 頼み方 |
|---|---|
| ありきたりを出させて捨てる | 「このテーマでよくあるアイデアを10個出して」→ それ以外を考える |
| 掛け算させる | 「図鑑とオンライン対戦と毎日変わる世界を組み合わせた作品を5案」 |
| 仕組みだけ分解させる | 「Kahoot!が盛り上がる理由を、仕組みで5つに分けて」 |
| 天井の足し方を相談する | 「この企画に、AI・リアルタイム・毎日変わる世界のどれを足すと一番化ける？」 |
| 技術のカタログにする | 「この作品をもっとすごくするのに使える技術を、易しい順に10個。全部、追加の費用なしで使えるもの」 |
| 使う人を演じさせる | 「小学3年生として、このゲームの第一印象を正直に言って」 |

### 企画・設計：言葉にできないことを引き出す

| 使い方 | 頼み方 |
|---|---|
| 先に質問させる（一番効く） | 「作り始める前に、わからないことを私に5つ質問して」 |
| 伝説版から削る | 「私のアイデアを、プロのチームが本気で作ったらどうなる？普通版・すごい版・伝説版の3段階で、遊んだ人が何を体験するかで説明して」→「伝説版を目指す設計にして。今回の10時間では、どこまで作れる？」 |
| 見積もりと削る提案 | 「残り6時間で作れる？無理なら何を削る？」 |
| 小さく分ける | 「1回30分で終わるタスクに分けて、確かめ方と順番も」 |

## 12. 「思ったより低レベル」を防ぐ

### 原因は3つ

1. **知らないから頼めない**：何ができるかを知らないので、頼み方がぼんやりし、AIは平均的なものを返す
2. **AIが楽をする**：難しい部分をダミーやごまかしで済ませ、「できました」と言う
3. **大きくなると壊れて妥協する**：機能を足すたびに壊れ、直せずに簡単版へ戻る

### 核心：考えさせるのではなく、選ばせる

人は、自分で言葉にできるものより、ずっと高いレベルのものを「こっちが良い」と見分けられます。そこで役割を入れ替えます。

- **AIが上限を広げる**（子どもが想像できない案を出す）
- **子どもは体験して選ぶ**（触って「こっち」と決める）
- **AIが外の基準で採点して引き上げる**（プロの基準と比べて足りないところを埋める）

### 早見表

| 症状 | 原因 | 対策 |
|---|---|---|
| どこかで見たようなもの | 知らないから平均的に頼んだ | 試食会、技術のカタログ、ありきたりを捨てる |
| 動くけど手触りが安っぽい | 語彙がない、7層が空っぽ | 言葉カード、7層シート、手触りを磨かせる |
| すごそうに見えて中身が空 | AIのごまかし | 完成品と伝える、正直に言わせる、AGENTS.md |
| 途中で全部作り直しになった | 将来の計画を伝えていない | 伝説版を目指す設計、将来の計画を最初に伝える |
| 終盤に壊れて、簡単版に戻した | 巨大なファイル、確かめる手段がない | 300行で分ける、デバッグ画面、テスト |
| 中身が少なくて薄い | 量を手で作っている | データ化して、AIに量産させる |
| 時間切れ | 簡単なところから作った | 一番難しいところから |
| 品質がAIの即席コードどまり | ゼロから書かせた | 定番のライブラリを使わせる |
| 子どもの想像の範囲で止まる | AIに提案させていない | 提案ループ、3案から選ぶ、専門家レビュー |

## 13. 品質の7層シート

ショボく見える作品は、たいてい機能は動いているけれど、下の層のどれかが空っぽです。①〜④はAIに頼むだけで一気に上がる、一番安い品質向上です。

| 層 | ショボい状態 | プロの状態 | 頼み方の例 |
|---|---|---|---|
| ① 統一感 | 色・文字・素材がばらばら | 色3〜4色、文字1〜2種、素材は同じタッチ | 「配色とフォントのルールを決めて、全画面に当てて」 |
| ② 動き | パッと出てパッと消える | 出る・消える・動くに、すべて加速と減速がある | 「全部の動きにイージングを付けて」 |
| ③ 反応 | 押しても何も起きない | どの操作にも0.1秒以内に、見た目と音で返事がある | 「すべての操作に、見た目と音の反応を付けて」 |
| ④ 音 | 無音 | 操作音・成功音・失敗音・BGM | 「効果音を自動生成して、場面ごとに当てて」 |
| ⑤ 量と多様さ | 敵1種類、ステージ1つ | データ化してAIが量産 | 「敵を10種類、性格の違いが分かるように」 |
| ⑥ 迎え入れ | いきなり本編、説明は文章 | タイトル → 30秒で遊び方が分かる → 本編。エラー時の表示、スマホ対応 | 「最初の30秒の体験を設計して」 |
| ⑦ 驚き | どこも同じ温度 | 誰もが「おっ」となる瞬間が1つある | 「思わず声を出す瞬間を1つ作るなら何？」 |

**驚きの1つに、全体の時間の3割を使う。** すべてを80点にするより、1つの場面を120点にするほうが「想像以上」に見えます。

## 14. 安全と公開のルール

### 公開前チェック

まずAIに「公開前の安全点検をして。下の項目を全部見て」と点検させ、そのあと本人と先生が確認します。

| チェック項目 | なぜ必要か |
|---|---|
| 鍵や秘密の値がコードに入っていない | 盗まれると悪用される |
| 利用者の入力を innerHTML で表示していない | 他人の画面で悪いプログラムが動く（XSS） |
| AIに渡す入力が、AIの指示を書き換えられない | 「前の指示を無視して…」攻撃（プロンプトインジェクション） |
| 書き込みやAIの呼び出しに回数制限がある | 荒らし、DeepSeek残高の消耗 |
| 本名・顔・学校名・住所が出ない | 個人情報 |
| 既存作品の名前・キャラ・画像・音楽を使っていない | 著作権 |
| 書き込み機能があるなら、AIか先生のチェックが入る | いじめ・不適切な投稿 |
| 画像生成サービスの素材は、そのサービスの規約で公開に使ってよい | 規約違反 |
| 遊び方と、作者のニックネームが書いてある | 本物の利用者のため |

### 公開範囲のルール

- サブドメインは、本名ではなく**ニックネームかID**にする。
- 書き込み・チャット・SNS系の作品は、まずクラス限定で公開する（Cloudflare Access で、許可した人だけが入れるようにする）。全体公開は、先生が判断してから。
- 公開後に荒らしや不適切な使われ方があれば、すぐに非公開に戻せるようにしておく。

### DeepSeekの注意（ai06から継続）

- 入力は中国のサーバーで処理・保存される。**個人情報を入れない。**
- 作品の中でAIに渡す利用者の入力にも、同じ注意が必要（作品の注意書きに書く）。

### Workers AIについて

Cloudflareの Workers AI（サーバー側での画像生成・音声認識・翻訳）には1日の無料枠がありますが、有料プランでは超えた分が課金されます。使う場合は、中継Workerで1日の上限を設けてください。費用ゼロの方針を優先するなら、使わない判断でかまいません。

## 15. 作品の回し方（提出から公開まで）

### 流れ

```
[生徒PC] Zed＋AIで開発 → 手元のブラウザで確認（Cloudflareにはログインしていない）
     │
     │  AIに「提出して」→ dev ブランチに送る（その子のリポジトリだけに書ける鍵を使う）
     ▼
[GitHub] akkyunity/（名前） の dev
     ▼
[先生] dev の中身を確認 → main に反映（Pull Request をマージ）
     │  Workers Builds が自動で本番に公開する
     ▼
https://（名前）.kaizuacademy.com（スマホや友達の端末での確認は、公開したあとにここで行う）
```

### この形にする理由

- **生徒にCloudflareの権限を一切渡さずに済む。** 生徒のPCにあるのは、自分のリポジトリにだけ書ける鍵だけ。
- **公開の前に必ず先生の目が通る。** 生徒は `main` に送らない（前提ファイルにも書いてある）。
- **履歴が全部残る。** 5カ月の成長が記録になり、壊れても前の状態に戻せる。

### セーブ（git）の扱い

生徒はgitのコマンドを覚えなくてかまいません。「セーブして」「提出して」「さっきのセーブに戻して」とAIに頼めば十分です。

## 17. 想定トラブルと対処

| 起きること | 対処 |
|---|---|
| AIが全部を書き直し始めた | 止めて、セーブに戻す。「計画を見せて、許可を取ってから」と頼む（AGENTS.mdにも書いてある） |
| AIがタスクを消して「全部終わりました」と言う | セーブに戻す。AGENTS.mdの「タスクは済みの印だけ」を読ませる。繰り返すならJSON形式に切り替える |
| すごそうに見えて、中身がダミーだった | 「ダミーや仮のデータを使っている場所を全部教えて」と聞き、1つずつ本物にする |
| 1つのファイルが巨大になり、AIが正しく直せない | 「役割ごとにファイルを分けて。動きは変えないで」 |
| 会話が長くなって、AIが混乱している | 新しい会話を始めて、開発日誌・タスク・決めたことを読ませる |
| リストにないライブラリを使われた | 「ライブラリ.mdにあるものだけで作り直して」 |
| 手元のブラウザで動かせない | AIに「手元で動かして」と頼み、ターミナルのエラーを全文渡す。Node.jsが入っているか確認 |
| ゲームが真っ白 | F12 → Consoleの赤いエラーを全文、バグの伝え方の型で渡す |
| AIを使う機能が動かない | 中継Workerの回数上限、DeepSeekの残高（エラー402）を確認 |
| 作品内のAIが変なことを言う | 作品内のAIへの指示文を見直す。中継Workerのフィルタを確認 |
| スコープが大きすぎて終わらない | 企画書の「今回の範囲」を見直す。「残り◯時間で作れる？何を削る？」とAIに聞く |
| 公開後に荒らされた | すぐ非公開に戻す。クラス限定にしてから再公開 |
| 前回のことを本人もAIも覚えていない | 開発日誌を読ませる。開発日誌が空なら、次回から最後の15分を必ず確保する |
| 天井の要素がどうしても動かない | 体験デモで20分試してだめなら、別の方向へ。銅で完成させることを優先する |
